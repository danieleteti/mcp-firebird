# 0.7.0 — More of the DBA's toolbox

- **Date:** 2026-11-06
- **Status:** Phase 1 implemented. Phases 2 and 3 are recorded so the decision is not lost.
- **Author:** Daniele Teti (with Claude)
- **Scope:** free edition only — ordinary SQL over an ordinary connection, no Services Manager, no file on the server
- **Touches:** `Firebird.Introspection`, `Firebird.DocGen`, `Firebird.SchemaAudit`, `Firebird.Activity`, `Firebird.Attachments`, `Firebird.Capabilities`, `providers/FirebirdToolsU`, `providers/FirebirdPromptsU`

## 1. What was missing

Four things a DBA asks and the server could not answer:

| Question | What was there |
|---|---|
| What is inside this procedure or trigger? | `fb_generate_documentation` listed them with signatures; the source was not shown |
| What does this column really contain? | `Firebird.SchemaAudit.ColumnStats` existed; no tool exposed it |
| How long does this query take, really? | One measured run, which pays for cold caches |
| Is anyone reading the data in clear text? | Nothing |

And two things the documentation already knew and did not print: a table's foreign keys
(`GetForeignKeys` was written and never rendered) and `COMMENT ON COLUMN` text.

## 2. Phase 1 — 0.7.0

1. **`fb_describe_object(name, kind?)`.** The PSQL source of a procedure, trigger, function or
   package, with the signature or the event it fires on. A name can belong to several kinds, so
   when it does and `kind` is absent the tool says which and asks, instead of choosing.
2. **`fb_column_stats(table_name, columns?)`.** Rows, NULL fraction, distinct values and
   selectivity from **one scan**, beside the stored selectivity of the index that leads on the
   column. "Stale" is `IsStale`, the same function `fb_audit_table` uses, so the two cannot
   disagree. Column names are matched against the catalogue before they reach the SQL. If the
   engine refuses the combined statement (a column type `COUNT(DISTINCT)` cannot take), it falls
   back to one scan per column and reports the refusal against its own column. BLOBs are left out
   of the default list.
3. **`runs` (1–10) on `fb_analyze_query`.** Fastest, median and slowest. Records and pages are
   reported for the first run only, since later runs hit warm caches. A first run over 5 seconds
   is not repeated: a query that slow is the finding.
4. **Wire encryption.** `MON$ATTACHMENTS.MON$WIRE_ENCRYPTED` exists from 4.0; it is absent from
   3.0.14 (measured on the kits, not taken from release notes), so `HasWireEncryptionMon` is
   `Ordinal >= 400` and the section is simply missing below that. A local attachment has no wire
   and is never counted. Shown in `fb_monitor_attachments` and repeated in `fb_audit_security`.
   The advisory suggests `WireCrypt = Required` as a comment; the server never reads
   `firebird.conf`.
5. **Prompts:** `migration_planning`, `schema_design_review`, `security_audit`. They work from
   tool output. Behaviour that differs between Firebird versions is sent to the release notes of
   the target version rather than asserted from memory.
6. **`fb_generate_documentation`** renders foreign keys and column descriptions. The description
   column appears only on tables where somebody wrote one.

Each item touches `sources/`, `providers/`, a DUnitX fixture, `docs/tools.md` and the README. A
new free tool or prompt also breaks the Python suite shared with the Enterprise repo until the
Enterprise exe is rebuilt.

## 3. Phase 2 — Enterprise repo

`fb_validate_database` (gfix through the Services Manager). A second backup tool (`nbackup`) would
be a second sanctioned process in the allowlist of `tests/check_core_boundary.ps1`; decide
separately.

## 4. Phase 3 — only on request

- Several databases per server: the design is in the project memory (named profiles in the flat
  `.env`, an optional `database` argument on every tool, never a stateful "use database").
- An HTTP transport with a Bearer key, loopback only. Depends on `mcp-server-delphi`; "stdio and
  read-only" is a selling point today.

## 5. Not done, and why

Free-form writes, per-table policy and data masking, server events, batch tools. They pull the
product towards a database gateway, which is not what this server is for: it answers a DBA's
questions and leaves the changes to the person who runs the statements.
